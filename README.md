# Smart Campus Sensor and Room Management API

A JAX-RS REST API for the University of Westminster 5COSC022W *Client-Server Architectures* coursework. Implements room and sensor management for a smart-campus system, with sub-resource readings, query-parameter filtering, and exception-mapped error handling.

---

## API design overview

| Concept | Endpoint | Notes |
|---|---|---|
| Discovery | `GET /api/v1/` | API metadata + collection links |
| Rooms collection | `GET /api/v1/rooms` `POST /api/v1/rooms` | List / create |
| Single room | `GET /api/v1/rooms/{roomId}` `DELETE /api/v1/rooms/{roomId}` | Read / decommission |
| Sensors collection | `GET /api/v1/sensors[?type=…]` `POST /api/v1/sensors` | List + filter / register |
| Sub-resource readings | `GET /api/v1/sensors/{sensorId}/readings` `POST /api/v1/sensors/{sensorId}/readings` | History / append |

**Technology stack**

- Jakarta JAX-RS via the **Jersey 2.34** implementation (no Spring Boot, no JEE container).
- Embedded **Grizzly** HTTP server on port 8080.
- JSON serialisation via **Jackson** (`jersey-media-json-jackson`).
- All persistence is **in-memory** using `ConcurrentHashMap` instances inside `InMemoryStore` — no database is used, as mandated by the brief.

**Cross-cutting concerns**

- `LoggingFilter` implements both `ContainerRequestFilter` and `ContainerResponseFilter` and prints the HTTP method, URI, and final status for every request/response pair.
- Custom exception mappers convert business exceptions into HTTP 409 (`RoomNotEmptyException`) and 422 (`LinkedResourceNotFoundException`) responses with clean, stack-trace-free bodies.
- A 403 response is returned when readings are posted to a sensor whose status is `MAINTENANCE`.

## Build and run

### Prerequisites

- **JDK 23** (the `pom.xml` is configured for Java 23 — change `maven.compiler.source` and `target` if you have an older JDK).
- **Apache Maven 3.6+**.

### Step-by-step

```bash
# 1 — clone or open the project folder
cd "Smart Campus"

# 2 — fetch dependencies and compile
mvn clean compile

# 3 — start the embedded server (leave the terminal open)
mvn exec:java -Dexec.mainClass=org.example.ServerMain
```

When the server is ready you will see:

```
Started listener bound to [0.0.0.0:8080]
[HttpServer] Started.
Smart Campus API running at http://0.0.0.0:8080/api/v1/
Press ENTER to stop.
```

To shut the server down, press **ENTER** in that terminal.

### Run the unit tests

```bash
mvn test
```

`ApiSmokeTest` exercises the discovery endpoint, room CRUD, the 422 mapper, the 409 mapper, and the 403 maintenance scenario through Jersey's in-process test framework.

## Sample curl commands

> The room/sensor IDs returned below are UUIDs generated by the server — substitute the actual values when running these manually.

### 1. Discovery

```bash
curl -i http://localhost:8080/api/v1/
```

### 2. Create a room

```bash
curl -i -X POST http://localhost:8080/api/v1/rooms \
     -H "Content-Type: application/json" \
     -d '{"name":"Library Quiet Study","capacity":30}'
```

### 3. Register a sensor inside that room

```bash
curl -i -X POST http://localhost:8080/api/v1/sensors \
     -H "Content-Type: application/json" \
     -d '{"roomId":"PASTE-ROOM-ID","type":"Temperature","name":"Temp Sensor 1","status":"ACTIVE"}'
```

### 4. Filter sensors by type (query parameter)

```bash
curl -i "http://localhost:8080/api/v1/sensors?type=Temperature"
```

### 5. Append a reading (sub-resource locator)

```bash
curl -i -X POST http://localhost:8080/api/v1/sensors/PASTE-SENSOR-ID/readings \
     -H "Content-Type: application/json" \
     -d '{"value":22.5,"unit":"C"}'
```

### 6. Read history for a sensor

```bash
curl -i http://localhost:8080/api/v1/sensors/PASTE-SENSOR-ID/readings
```

### 7. Trigger 422 (linked resource not found)

```bash
curl -i -X POST http://localhost:8080/api/v1/sensors \
     -H "Content-Type: application/json" \
     -d '{"roomId":"does-not-exist","type":"CO2"}'
```

### 8. Trigger 409 (delete a room with sensors)

```bash
curl -i -X DELETE http://localhost:8080/api/v1/rooms/PASTE-ROOM-ID
```

## Conceptual report 

### JAX-RS Resource Lifecycle (Part 1.1)

In JAX-RS (and Jersey by default), resource classes are typically **per-request**: a new instance of a resource class is created for each incoming HTTP request. A resource only behaves like a singleton if it is explicitly registered/managed that way (for example, registering a single instance or using a DI container with singleton scope).

In this project, request-to-request state is stored in the in-memory maps (see `InMemoryStore`), not in resource object fields, so the observable API state persists regardless of whether Jersey uses per-request resource instances. The maps are `ConcurrentHashMap` instances, which gives thread-safe individual operations and prevents data loss or race conditions when Jersey serves concurrent requests on multiple threads.

### Hypermedia / HATEOAS (Part 1.2)

HATEOAS (Hypermedia as the Engine of Application State) is an advanced REST design feature because responses don't just return data; they also include **links and available actions** that guide the client through the application dynamically (instead of the client hardcoding URL structures).

It's "advanced" because it requires careful design of representations (link structure, relation types, consistency, versioning strategy), more complex testing, and often adoption of a hypermedia format (e.g., HAL, Siren, JSON:API). The payoff is **looser coupling** between client and server and safer evolvability of endpoints.

#### Short HATEOAS example

Instead of returning only raw data/paths, a hypermedia response can embed links that a client can follow:

```json
{
  "version": "v1",
  "_links": {
    "self": { "href": "/api/v1/" },
    "rooms": { "href": "/api/v1/rooms" },
    "sensors": { "href": "/api/v1/sensors" }
  }
}
```

### Returning IDs vs Full Objects in a Room List (Part 2.1)

Returning only IDs minimises bandwidth but forces the client into N additional round-trips to render any meaningful view, which inflates latency on slow networks. Returning full room objects eliminates that chatty pattern and lets clients render lists immediately, at the price of larger responses. For a campus dashboard, full-object responses are preferable because the list view almost always needs the name and capacity. Modern compromises include selectable field projection (`?fields=id,name`) and pagination.

### Idempotency of DELETE Requests (Part 2.2)

An operation is **idempotent** if repeating it results in the same final server state.

`DELETE /rooms/{roomId}` is *conceptually idempotent*: once the room is deleted, further deletes do not "delete it more." It's common for APIs to return:

- First delete: `200 OK` or `204 No Content`
- Subsequent delete: `404 Not Found`

Even if the status code changes, the final state is still the same (room absent), so DELETE remains idempotent in the REST sense. The 409-blocked case (delete attempted while sensors still attached) is also idempotent in effect because it never mutates state.

### Format Mismatch in POST Requests / @Consumes (Part 3.1)

If a client sends a payload in the wrong format—e.g., `Content-Type: text/plain` to an endpoint that expects JSON (`@Consumes(application/json)`):

- The server may respond with **415 Unsupported Media Type** (or sometimes **400 Bad Request** if parsing fails differently).
- The resource method may **not execute**, because the framework rejects the request before invocation.
- The result is a failed operation: no resource is created/updated, and the client must fix headers and/or payload formatting.

Correct `Content-Type` headers are essential for reliable client/server integration.

### Query Parameters vs URL Path (Filtering Sensors) (Part 3.2)

#### Query parameters (recommended for filtering)

Example: `GET /api/v1/sensors?type=temp`

- **Pros**: natural for optional filters; easy to extend (`?type=temp&status=ACTIVE`); avoids route explosion; cache-friendly.
- **Cons**: slightly less "sub-collection-like" than a dedicated path.

#### URL path elements (better for strict hierarchy)

Example: `GET /api/v1/sensors/type/temp`

- **Pros**: can read like a distinct sub-collection.
- **Cons**: awkward when multiple optional filters exist; more routes to maintain; harder to evolve as filtering grows.

For this project's "filter by type if present" behavior, **query parameters are the clearer and more scalable choice**.

### Sub-Resource Locator Benefits (Part 4.1)

The locator method on `SensorResource` simply returns a new `SensorReadingResource` instance, into which the parent `sensorId` is captured via the constructor. This produces three benefits: separation of concerns (each class stays small and focused); contextual state (every method inside the sub-resource already knows which sensor it is operating on); and maintainability (new nested areas like `/sensors/{id}/alerts` become their own class instead of yet another method block on a thousand-line controller).

### Why 422 over 404 for Missing References (Part 5.2)

`404 Not Found` describes a resource that the URL itself points to and cannot be located. `422 Unprocessable Entity` describes a different failure: the URL was correct, the JSON was valid, but a foreign-key-style reference inside the body pointed to a non-existent room. Returning 404 in that case would mislead the client into thinking the `/sensors` endpoint was unreachable, when the real problem is a business-rule rejection on the body. 422 keeps the protocol semantics clean and makes API consumers easier to write because they can branch on status alone — 404 means "fix the URL", 422 means "fix the body".

### Cybersecurity Risk of Stack Traces (Part 5.4)

A leaked Java stack trace gives an attacker library and framework versions (which can be cross-referenced against CVE databases), the package and class structure of the application, absolute filesystem paths and usernames from compiled-in line numbers, JDBC URL hints from any connection-related exception, and method names that suggest where authentication and authorisation logic live. In the worst case a SQLException trace can reveal the schema or part of the offending query. OWASP classes this as Security Misconfiguration. The mitigation is a global `ExceptionMapper<Throwable>` that catches everything, logs the full trace server-side for operations, and returns a generic `500 Internal Server Error` with a correlation id to the client.

### Filters vs Inline Logger.info() (Part 5.5)

Inlining `Logger.info` calls in every resource method is repetitive, easy to forget on new endpoints, and pollutes the readable intent of each method body. The JAX-RS filter approach centralises the concern: my `LoggingFilter` implements both `ContainerRequestFilter` and `ContainerResponseFilter`, and Jersey automatically calls them for every inbound request and outbound response — including responses that originate inside an exception mapper, which an inline approach would miss. The filter also captures information uniformly so log-analysis tools see a consistent format, and any later upgrade (correlation id, request timing, slow-request alerts) happens in one file rather than every controller. This is the standard separation-of-concerns argument behind aspect-oriented programming and middleware in other web frameworks.
